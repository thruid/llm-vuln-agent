## 1. 项目解决什么问题

### 1.1 传统漏洞分析流程

一个渗透测试工程师拿到资产探测结果（IP、端口、协议、服务、版本、Banner）后，通常要做：

1. 识别服务与产品（"8080 端口返回 `Apache Tomcat` banner"）
2. 去 CVE 库 / 漏洞情报里查这个产品、这个版本有哪些已知漏洞
3. 逐个判断：漏洞是否适用于这个**具体版本**（版本区间匹配）
4. 挑选验证方式，写脚本 / 用工具**验证**漏洞是否真实存在
5. 收集证据，输出结论：`存在 / 不存在 / 不确定`

这套流程高度依赖人的经验，且重复、容易漏、结论不透明（"我判断它存在"但证据链不全）。

### 1.2 本系统的目标与边界

用 **LLM Agent（决策）+ RAG（知识）+ Tool Calling（执行）** 把上述流程自动化：

- **LLM 负责理解、分析与决策** —— 决定"下一步该查什么、该验证哪个 CVE"
- **RAG 负责提供漏洞知识** —— 用向量检索从知识库里捞出候选 CVE
- **Tool Calling 负责调用安全工具** —— 但工具是**白名单**封装的，LLM 不能执行任意命令
- **Verification Engine 负责实际验证** —— 独立于 LLM，产生可追溯的证据

**边界**（安全红线，贯穿全文）：

- 只用于自建靶场 / CTF / 明确授权的资产，**不实现**对公网目标的自动化攻击
- LLM 不做扫描器，不直接跑 shell
- 结论必须是 `CONFIRMED / NOT_VULNERABLE / UNCERTAIN` 三态，信息不足宁可 `UNCERTAIN`

## 2. 三个核心技术概念

### 2.1 LLM Agent：把「模型」变成「能循环做事的程序」

大模型本身是**无状态**的：给它一段文字，它返回一段文字。所谓 Agent，是在外面包一个**循环**，让模型反复"观察 → 决策 → 行动 → 再观察"：

```python
while not finished:
    observation = get_state()          # 观察当前状态
    decision = llm.invoke(observation) # 模型做一次决策
    if decision.type == "tool_call":
        result = execute_tool(decision) # 执行工具
        update_state(result)            # 把结果写回状态
    elif decision.type == "final":
        return decision                 # 结束
```

关键点：

- **状态（state）是显式的**，不靠模型"记忆" —— 模型每次只看到最新状态的摘要。
- **模型只输出一个决策**（JSON），而不是"自由发挥" —— 决策要么是"调用某个工具"，要么是"给出最终结论"。
- **为什么不能把 LLM 当扫描器**：模型没有真实感知能力，直接问它"这个目标有没有漏洞"它会基于训练知识"编"。所以流程里把"判断"交给模型、"感知/验证"交给工具，模型只能引用工具返回的**证据**下结论。

### 2.2 RAG：给模型外挂一个可检索的知识库

模型训练数据是"过去"的、且不能覆盖所有 CVE 细节。RAG（Retrieval-Augmented Generation）的思路是：

```
CVE 数据源 → 清洗 → 结构化 → 切成 Document → Embedding（向量化）→ 向量数据库 → 检索
```

查询时，把资产的「产品 + 版本 + 服务」转成**同一向量空间**里的向量，去库里找最相似的 CVE 文档，再把这些文档作为**上下文**交给模型。这样模型得到的是"检索回来的事实"，而不是"凭记忆猜"。

**注意**：本项目**没有只用向量相似度**。向量检索擅长语义相关，但漏洞匹配更要紧的是**精确的产品/版本匹配**。所以检索是"向量 + 结构化过滤"的混合（详见 [4.3](#43-rag-层-rag)）。

### 2.3 Tool Calling：给模型"手"，但不给"钥匙"

Tool Calling（函数调用）让模型能通过**结构化 JSON** 请求执行某个预定义函数：

```json
{"type": "tool_call", "tool": "vulnerability_verify",
 "arguments": {"ip": "127.0.0.1", "port": 8080, "cve": "CVE-2021-41079", "verification_id": "mock"}}
```

安全上的关键设计：**模型只能请求"注册过的工具"，且每个工具有 `input_schema` 做参数校验、有 `boundary` 做权限边界**。模型永远接触不到"任意 shell 命令"这个能力 —— 它没有这把钥匙。

## 3. 总体架构与数据流

```
输入资产 Asset
     │
     ▼
┌──────────────────────────────────────────────────────────┐
│  Agent 循环 (agent/agent.py)                              │
│  Observe → Analyze → Retrieve → Plan → Tool Call → ...    │
│                                                          │
│   ┌─────────┐  decide()  ┌──────────────────────────┐    │
│   │   LLM   │◄──────────►│  planner / state / memory │    │
│   └─────────┘            └──────────────────────────┘    │
│        │ tool_call                                        │
│        ▼                                                  │
│  ToolRegistry (tools/registry.py)                         │
│    ├─ port_scan / service_detect / version_detect         │
│    ├─ vulnerability_search  ──► RAG Retriever             │
│    ├─ vulnerability_verify  ──► Verification Engine        │
│    └─ result_parser                                       │
└──────────────────────────────────────────────────────────┘
     │
     ▼
结构化报告 Report (JSON / Markdown)
```

依赖方向（单向，避免循环依赖）：

```
models  ←  vulnerability  ←  rag  ←  tools  ←  agent  ←  pipeline  ←  main
              ▲                              ▲
              └────────  verifier ───────────┘
```

- `models` 最底层，只有数据类，不 import 任何业务模块。
- `vulnerability` 依赖 `models`（版本比较、匹配、验证）。
- `rag` 依赖 `models` + `vulnerability`（知识库、检索）。
- `tools` 依赖 `models` + `rag` + `vulnerability`（工具封装）。
- `agent` 依赖 `tools`（循环调用工具）。
- `pipeline` 把上面所有组件**装配**起来（工厂模式）。
- `main` 只做命令行解析 + 调用 pipeline。

## 4. 分层逐模块讲解

### 4.1 数据模型层 `models/`

核心思想：**用 dataclass 表达"纯数据"，序列化靠 `to_dict/from_dict`，不引入 Pydantic 依赖**。

#### `Asset`（资产）

```python
@dataclass
class Asset:
    ip: str
    port: int | None = None
    protocol: str = "tcp"
    service: str | None = None      # "http"
    product: str | None = None      # "Apache Tomcat"
    vendor: str | None = None
    version: str | None = None      # "9.0.50"
    banner: str | None = None
    extra: dict = field(default_factory=dict)

    @property
    def target(self) -> str:
        return f"{self.ip}:{self.port}" if self.port is not None else self.ip
```

> **学习点**：资产探测结果可能是**不完整**的（只有 IP+端口，没有产品版本）。所以除了 `ip` 其余字段都可选。后续 Agent 可以用 `service_detect` / `version_detect` 工具来"补全"资产 —— 这就是"资产分析"环节。

#### `Vulnerability`（漏洞/CVE）

```python
@dataclass
class Vulnerability:
    cve_id: str
    product: str
    vendor: str = ""
    affected_versions: list[str] = field(default_factory=list)  # ["<9.0.54"]
    fixed_versions: list[str] = field(default_factory=list)
    vulnerability_type: str = ""
    description: str = ""
    prerequisites: str = ""        # 验证前置条件（人类可读）
    verification_method: str = ""  # 验证方法说明
    verification_id: str = ""      # 对应某个已注册的验证器 key
    references: list[str] = field(default_factory=list)
    severity: str = ""
    cvss_score: float = 0.0
```

`to_document_text()` 把这条记录渲染成一段文本，作为 Embedding 的输入：

```python
def to_document_text(self) -> str:
    pieces = [f"CVE: {self.cve_id}", f"Vendor: {self.vendor}", ...]
    return "\n".join(...)
```

> **学习点**：`verification_id` 是关键字段 —— 它把"知识库里的漏洞描述"和"实际能执行的验证器"**解耦**。知识库只说"这个 CVE 该用哪种验证方式"，具体怎么验证由 `vulnerability/verifier.py` 里的注册表决定。

#### `Result`（结果）—— 三态判定是核心

```python
class FinalStatus(str, Enum):
    CONFIRMED = "CONFIRMED"           # 确证存在
    NOT_VULNERABLE = "NOT_VULNERABLE" # 确证不存在（版本不匹配等）
    UNCERTAIN = "UNCERTAIN"           # 信息不足，不做猜测

class VerificationStatus(str, Enum):
    SUCCESS = "success"   # 验证执行成功（不代表漏洞存在）
    FAILED = "failed"     # 执行失败（如目标不可达、越权被拒）
    ERROR = "error"       # 内部错误

class VersionMatch(str, Enum):
    MATCH = "match"
    NO_MATCH = "no_match"
    UNCERTAIN = "uncertain"
```

> **学习点**：把「验证**执行状态**（success/failed/error）」和「漏洞**判定**（confirmed/not_vulnerable/uncertain）」分开。一个验证可能"执行成功"但结论是"不确定"，也可能"执行失败"（连不上目标）导致"不确定"。混在一起会丢掉信息。

### 4.2 版本比较与匹配 `vulnerability/`

这是整个系统**正确性**最关键的模块，也是最容易写错的模块。

#### 版本比较 `version.py`

不依赖 `packaging` 库，自己实现一套够用的语义：

1. **切分**：把 `"9.0.50"` 按 `.` 拆成段，每段解析成 `(是否数字, 数字, 后缀)`：

```python
@dataclass(frozen=True)
class _Token:
    is_numeric: bool
    number: int
    suffix: str

def _tokenize(version: str) -> list[_Token]:
    for part in _SPLIT.split(version.strip().lower()):  # 按 . - + _ 切
        m = _NUM.match(part)                              # "50" 或 "50p1"
        if m:
            tokens.append(_Token(True, int(m.group(1)), m.group(2)))
        else:
            tokens.append(_Token(False, 0, part))         # 纯文本段
```

2. **逐段比较**：

```python
def compare(a: str, b: str) -> int:
    ta, tb = _tokenize(a), _tokenize(b)
    for i in range(max(len(ta), len(tb))):
        if i >= len(ta): return -1            # a 更短 → a 更小（9.0 < 9.0.1）
        if i >= len(tb): return 1
        ai, bi = ta[i], tb[i]
        if ai.is_numeric != bi.is_numeric:
            return 1 if ai.is_numeric else -1 # 数字段 > 文本段（1.0 > 1.0-alpha）
        if ai.is_numeric:
            if ai.number != bi.number:
                return -1 if ai.number < bi.number else 1
            if ai.suffix != bi.suffix:         # 50 < 50p1
                return -1 if ai.suffix < bi.suffix else 1
        ...
```

3. **区间匹配**支持多种写法：

```
"*"                    任意版本
"9.0.50"               精确
"<9.0.54"              小于
">=8.0.0 <9.0.51"      复合（空格 = AND）
"8.0.0 - 9.0.50"       闭区间
"2.3.5 - 2.3.31, 2.5 - 2.5.10"   逗号 = OR
```

```python
def version_in_range(version: str, spec: str | list[str]) -> bool:
    for s in specs:
        alternatives = [p.strip() for p in s.split(",")]  # 逗号 = OR
        for alt in alternatives:
            if _matches_single(version, alt):
                return True
    return False
```

> **学习点**：版本比较是"启发式"而非严格语义版本。对于无法解析的写法，**上层把它当作 `UNCERTAIN` 而不是 `NO_MATCH`** —— 这是"不做强行猜测"原则在代码层的体现。

#### 漏洞匹配 `matcher.py`

把「产品匹配」「厂商匹配」「版本匹配」三个维度组合成一个判定：

```python
def version_match(self, asset, vuln) -> VersionMatch:
    version = (asset.version or "").strip()
    affected = vuln.affected_versions or []
    if not version or version in ("unknown", "n/a"):
        return VersionMatch.UNCERTAIN       # 没版本 → 不确定
    if not affected:
        return VersionMatch.UNCERTAIN       # 没受影响区间 → 不确定
    if any(v.strip() == "*" for v in affected):
        return VersionMatch.MATCH
    if version_in_range(version, affected):
        return VersionMatch.MATCH
    return VersionMatch.NO_MATCH
```

产品匹配用"归一化 + 子串包含"：

```python
def normalize_name(value):  # "Apache Tomcat" -> "apache tomcat"
    value = value.lower()
    value = re.sub(r"[^a-z0-9]+", " ", value)
    return " ".join(value.split())
```

### 4.3 RAG 层 `rag/`

数据流：`document_loader` → `embedding` → `knowledge_base` → `retriever`。

#### Embedding（向量化）`embedding.py`

默认 `HashingEmbedder` 是**特征哈希**（feature hashing）：把文本切成「词 + 字符 3-gram」，每个 token 哈希到固定维向量的一位并累加符号，最后 L2 归一化：

```python
def _tokenize(text):
    words = _WORD.findall(text.lower())     # 词
    grams = set()                            # 字符 3-gram（捕捉子词相似）
    for word in words:
        if len(word) >= 3:
            for i in range(len(word) - 2):
                grams.add(word[i:i+3])
    return words + sorted(grams)

def embed(self, text):
    vector = [0.0] * self.dim
    for token in _tokenize(text):
        digest = hashlib.md5(token.encode()).digest()
        index = int.from_bytes(digest[:4], "big") % self.dim   # 桶下标
        sign = 1.0 if (digest[4] & 1) else -1.0                # 随机符号
        vector[index] += sign
    return self._normalize(vector)          # 余弦相似度需先归一化
```

> **学习点**：
> - **为什么不用真实 Embedding 模型**：真实模型需要 API key 或本地模型权重，无法"零依赖离线可跑"。特征哈希给出的是"文本重叠度"信号，对 demo 足够，且**确定性**（同输入永远同输出）利于测试。
> - **为什么归一化**：归一化后向量点积 == 余弦相似度，检索时直接点积即可。
> - 接口是 `Embedder` Protocol，`OpenAIEmbedder` 可无缝替换。

#### 知识库 + 向量库 `knowledge_base.py`

```python
class KnowledgeBase:
    def add_vulnerabilities(self, vulns):
        for vuln in vulns:
            self._vulns[vuln.cve_id] = vuln
        self.rebuild_index()

    def rebuild_index(self):

        vectors = self.embedder.embed_batch([d.text for d in docs])
        self.store.add(ids, vectors, metadatas)
```

`InMemoryVectorStore` 是纯 Python 暴力余弦检索，但接口对齐 Milvus 风格（`add / search / clear / __len__`），方便日后替换：

```python
class InMemoryVectorStore:

        scored = [SearchResult(id=..., score=_cosine(query_vector, self._vectors[i]), ...)]
        scored.sort(key=lambda r: r.score, reverse=True)
```

#### 混合检索 `retriever.py`（重点）

**只靠向量相似度不够**，所以检索分两步：

```python
def retrieve(self, asset, top_k=None):
    query_vector = kb.embedder.embed(self._query_text(asset))
    semantic = kb.store.search(query_vector, top_k=max(top_k * 3, 10))  # 先多捞

    for s in semantic:
        vuln = kb.get(s.id)
        outcome = self.matcher.match(asset, vuln)     # 结构化匹配
        product_bonus = 1.0 if outcome.product_match else 0.0
        vendor_bonus = 1.0 if outcome.vendor_match else 0.0
        score = (semantic_weight * s.score
                 + product_weight * product_bonus
                 + vendor_weight * vendor_bonus)
        hits.append(RetrievalHit(..., version_match=outcome.version_match.value, ...))
    hits.sort(key=lambda h: h.score, reverse=True)
    return hits[:top_k]
```

几个关键设计：

- **先多捞（oversample）再精排**：语义检索取 `top_k*3`，让结构化过滤有足够的候选池。
- **最终 `score` 是三信号加权**：语义相似度 0.5 + 产品匹配 0.35 + 厂商匹配 0.15（可在 `config.yaml` 调）。
- **`RetrievalHit` 同时带上 `version_match`**（match/no_match/uncertain），这样 Agent 拿到候选时就知道"哪些是版本匹配、值得验证"，而不必自己再算一遍。

`RetrievalHit.version_match` 的 `is_version_candidate` 属性：

```python
@property
def is_version_candidate(self) -> bool:
    return self.product_match and self.version_match != VersionMatch.NO_MATCH.value
```

### 4.4 工具层 `tools/`

#### 统一 Tool 接口 `base.py`

```python
class Tool(ABC):
    name: str
    description: str
    input_schema: dict    # JSON Schema 子集
    output_schema: dict
    requires_network: bool = True
    boundary: str = "target_allowlist"

    @abstractmethod
    def execute(self, **kwargs) -> dict: ...

    def validate(self, arguments) -> list[str]:   # 用 input_schema 校验
        return validate_against_schema(arguments, self.input_schema)
```

**为什么每个工具都要声明 schema**：模型和人类都能据此知道"能传什么参数"，且执行前做严格校验，坏参数根本到不了网络层。

#### 安全边界 `boundary.py`

```python
class TargetAllowlist:
    def is_allowed(self, host) -> bool:
        # 先查 denylist（黑名单优先）
        # 再查 hostname 精确匹配 / IP / CIDR
    def assert_allowed(self, host):
        if not self.is_allowed(host):
            raise PermissionError(f"target {host!r} is outside the authorized allowlist")
```

**deny-by-default**：不在白名单（默认只有 `127.0.0.1/::1/localhost`）就拒绝。每个网络工具在执行前都调用 `assert_allowed`。

#### 工具注册与统一分发 `registry.py`

Agent 不直接调用工具，而是通过 `ToolRegistry`：

```python
def call(self, name, arguments) -> dict:
    tool = self.get(name)
    validation_errors = tool.validate(arguments)
    if validation_errors:
        return {"success": False, "tool": name, "error": "invalid arguments: ..."}
    try:
        output = tool.execute(**arguments)
    except PermissionError as exc:          # 越权
        return {"success": False, "tool": name, "error": str(exc)}
    except Exception as exc:                 # 任何工具异常
        return {"success": False, "tool": name, "error": f"{type(exc).__name__}: {exc}"}
    return {"success": True, "tool": name, "output": output}
```

> **学习点**：返回值统一成 `{success, tool, output, error}` 信封。这样 Agent 循环里**不会因为一个工具失败而崩溃** —— 失败会变成一条带 `error` 的观测，Agent 据此继续（对应测试场景「工具调用失败」）。

#### 六个工具

| 工具 | 关键实现 |
| --- | --- |
| `port_scan` | 纯 Python `socket.create_connection` 连端口，读 banner；先 `assert_allowed` |
| `service_detect` | banner 正则匹配 + 端口默认值表，返回 `service/product` |
| `version_detect` | 正则 `\b(\d+\.\d+(\.\d+)?...)\b` 从 banner 抽版本 |
| `vulnerability_search` | 包一层 `Retriever.retrieve`，返回候选 CVE 列表 |
| `vulnerability_verify` | 包一层 `VerificationEngine.verify`，返回结构化验证结果 |
| `result_parser` | 把原始输出文本分类成三态 |

### 4.5 验证引擎 `vulnerability/verifier.py`

验证引擎**独立于 LLM**，这是"LLM 负责判断、引擎负责验证"的落点。

```python
@dataclass
class VerificationTask:
    asset: Asset
    vulnerability: Vulnerability

class VerificationEngine:
    def verify(self, task) -> VerificationResult:
        # 1. 安全边界
        if not self.scope.is_allowed(task.host):
            return VerificationResult(status=FAILED, result=UNCERTAIN, error="outside allowlist")
        # 2. 无破坏性策略
        if self.non_destructive_only and not verifier.non_destructive:
            return VerificationResult(status=FAILED, result=UNCERTAIN, error="destructive blocked")
        # 3. 分发到对应验证器
        verifier = self._verifiers.get(vuln.verification_id or "mock")
        # 4. 运行 + 兜底异常
        result = verifier.verify(task)
```

内置验证器（全部**无破坏性**）：

| 验证器 | `verification_id` | 做什么 |
| --- | --- | --- |
| `MockVerifier` | `mock` | 离线确定性：有 `mock_result` 用指定值；否则按版本区间给**明确标注为模拟**的结论 |
| `BannerVerifier` | `banner_check` | 读服务 banner 作为版本证据 |
| `HttpPathVerifier` | `http_path_check` | GET 指定路径，检查状态码 + 正文标记 |
| `HttpHeaderVerifier` | `http_header_check` | 检查响应头标记 |

`MockVerifier` 的兜底逻辑体现了"证据透明"：

```python
if version and affected and version_in_range(version, affected):
    return CONFIRMED, 0.8, f"mock verifier: asset version {version} satisfies affected range {affected}"
```

证据字符串里**明确写了 "mock verifier"** —— 模拟结论不会被误当成真实探针结果。

> **学习点**：验证引擎的设计是"**前置条件检查 → 分发 → 运行 → 解析 → 证据 → 状态**"。真实系统里，`prerequisites` 字段、越权检查、破坏性拦截都在第 1、2 步完成，验证器本身只关心"怎么验"。

### 4.6 Agent 层 `agent/`

#### 状态 `state.py` + 记忆 `memory.py`

```python
@dataclass
class AgentState:
    asset: Asset
    candidates: list[dict] = field(default_factory=list)     # 候选 CVE
    verification_results: dict[str, dict] = field(default_factory=dict)  # cve_id -> 验证结果
    observations: list[dict] = field(default_factory=list)   # 逐步观测日志（可解释性）
    step: int = 0
    max_steps: int = 12
    search_attempted: bool = False
    finished: bool = False
    final_report: Report | None = None
```

`observations` 记录每一步（tool_call / retrieve / verify），最终报告之外的"过程可追溯"。

#### 决策 `planner.py` —— 确定性规划器

`plan_next` 是整个决策策略的**可测试**核心（`MockLLM` 直接调用它）：

```python
def plan_next(state) -> Decision:
    asset = state.asset
    if not (asset.product or asset.service or asset.version or asset.banner):
        return build_final(state)          # 信息不足，直接给 UNCERTAIN

    if not state.candidates:
        if state.search_attempted:
            return build_final(state)      # 查过了但没有候选 → 结束
        return Decision(type="tool_call", tool="vulnerability_search", arguments={...})

    pending = [c for c in state.candidates if _is_pending(c, state)]
    if pending:
        best = sorted(pending, key=lambda c: -c["score"])[0]
        return Decision(type="tool_call", tool="vulnerability_verify", arguments={...})
    return build_final(state)              # 都验完了 → 出报告
```

`_is_pending`（哪些候选值得验证）：

```python
def _is_pending(candidate, state):
    if not candidate.get("product_match"): return False          # 产品不匹配 → 跳过
    if candidate.get("version_match") == "no_match": return False # 版本不匹配 → 跳过
    if candidate.get("cve_id") in state.verification_results: return False  # 已验证 → 跳过
    return True
```

> **学习点**：把决策策略写成**纯函数**（输入 state、输出 Decision），好处是：① 单元测试直接覆盖；② `MockLLM` 离线用它；③ 真实 LLM 只是"用模型复现这套策略"（见 `prompts.py` 里的 instructions），策略本身有明确参照。

#### LLM 客户端 `llm.py`

```python
class MockLLM:
    name = "mock"
    def decide(self, state, tools) -> Decision:
        return planner.plan_next(state)   # 确定性

class OpenAICompatibleLLM:
    name = "openai"
    def decide(self, state, tools) -> Decision:
        messages = [{"role": "system", "content": build_system_prompt(tools)},
                    {"role": "user", "content": build_user_prompt(state)}]
        resp = client.chat.completions.create(model=..., messages=messages, ...)
        return self._parse(resp.choices[0].message.content)
```

两者实现同一个 `LLMClient` Protocol，`build_llm` 按配置选择。`OpenAICompatibleLLM._parse` 会把模型返回的 JSON（可能带 markdown 代码块）解析成 `Decision`。

#### Agent 循环 `agent.py`（前面已贴过，这里强调 `_execute` 的状态回写）

```python
def _execute(self, decision):
    result = self.registry.call(decision.tool, decision.arguments)
    if decision.tool == "vulnerability_search":
        state.search_attempted = True
        state.candidates = result["output"].get("candidates", []) if result["success"] else []
    elif decision.tool == "vulnerability_verify":
        cve = decision.arguments["cve"]
        if result["success"]:
            state.verification_results[cve] = result["output"]
        else:
            state.verification_results[cve] = {"result": "uncertain", "error": result["error"], ...}
    elif decision.tool == "service_detect" and result["success"]:
        state.asset.service = result["output"]["service"]   # 回写资产
```

> **学习点**：工具结果**如何影响下一次决策**是 Agent 的核心。这里把 `vulnerability_search` 的结果存进 `candidates`、把 `vulnerability_verify` 的结果存进 `verification_results`，而 `plan_next` 恰恰是读这两个字段决定下一步 —— 状态驱动闭环。

### 4.7 装配与流水线 `pipeline/`

#### 工厂 `factory.py`

把所有组件按配置装配成一个 `System`：

```python
@dataclass
class System:
    config, scope, knowledge_base, retriever, matcher,
    engine, registry, llm
```

`build_system()` 里关键装配顺序：

```python
scope = TargetAllowlist(allowed=..., denied=...)
embedder = build_embedder(provider, dim)
knowledge_base = KnowledgeBase(embedder)          # 载入 CVE JSON
knowledge_base.add_vulnerabilities(CVEDataLoader(cve_dir).load())
retriever = Retriever(knowledge_base, matcher, ...)
engine = VerificationEngine(scope=scope, ...)
registry = ToolRegistry(scope=scope)
registry.register(PortScanner(...)); ...; registry.register(VulnerabilityVerifierTool(kb, engine))
llm = build_llm(config.section("llm"))
```

> **学习点**：工厂模式让 `main.py` 和测试都能用同一套装配逻辑，且测试可以注入**自定义 CVE 数据目录**或覆盖配置（见 `tests/_helpers.py`）。

#### 工作流 `workflow.py` + 报告 `report.py` + 持久化 `storage.py`

- `run_workflow(asset, system)`：建 `AgentState` → `Agent.run()` → 补 `generated_at` → 返回 `Report`。
- `report_to_json / report_to_markdown`：渲染 11 个字段的报告（Target/Service/Version/CVE/Description/Verification Method/Verification Result/Evidence/Confidence/Final Status）。
- `ResultStore`：SQLite 存报告（stdlib `sqlite3`），`save/load/recent`。

## 5. 一个完整请求的执行追踪

输入：`Apache Tomcat 9.0.50, 127.0.0.1:8080`（`--product "Apache Tomcat" --version 9.0.50`）

| 步 | Agent 决策 | 发生了什么 | 状态变化 |
| --- | --- | --- | --- |
| 1 | `vulnerability_search` | RAG 检索候选 | `candidates` = 5 条（Tomcat 3 条 + nginx/OpenSSH 等），每条带 `version_match` |
| 2 | `vulnerability_verify(CVE-2021-41079)` | 版本 9.0.50 在 `<9.0.54` 内 → mock 验证器 CONFIRMED | `verification_results["CVE-2021-41079"]` = confirmed |
| 3 | `vulnerability_verify(CVE-2025-24813)` | 9.0.50 在 `9.0.0-M1 - 9.0.97` 内 → CONFIRMED | 同上 |
| 4 | `final` | 没有更多待验证候选 | 出报告 |

最终报告 3 条：

- `CVE-2021-41079` → `CONFIRMED`（版本匹配 + 验证）
- `CVE-2025-24813` → `CONFIRMED`（版本匹配 + 验证）
- `CVE-2020-1938` → `NOT_VULNERABLE`（版本 9.0.50 不在 `<9.0.31` 内，`version_match=no_match`，未验证直接判否）

> 注意第 3 条：`CVE-2020-1938`（Ghostcat）是"版本不匹配 → NOT_VULNERABLE"，**不需要**实际验证 —— 这体现了"版本匹配"作为第一道过滤，省去了无效验证。

再跑 `--version 9.0.60`：

- `CVE-2021-41079`、`CVE-2020-1938` → `NOT_VULNERABLE`（9.0.60 已修复这两个）
- `CVE-2025-24813` → `CONFIRMED`（9.0.60 仍 < 9.0.98）

这证明系统**不是**"有 CVE 就报"，而是真的按版本区间逐一判断。

## 6. 关键设计决策与权衡

| 决策 | 选择 | 理由 / 权衡 |
| --- | --- | --- |
| 数据类 | 标准库 `dataclass` | 零依赖、可序列化、类型清晰；放弃 Pydantic 的运行时校验，但 `Tool` 层用 schema 单独做参数校验 |
| Embedding | 特征哈希 | 零依赖、确定性、可离线；语义质量不如真实模型，但本场景结构化匹配占主导 |
| 向量库 | 内存暴力余弦 | 零依赖、demo 数据量小；接口对齐 Milvus，可替换 |
| LLM | `MockLLM` 默认 | 离线可跑可测；`OpenAICompatibleLLM` 同接口切换 |
| Agent 循环 | 手写 `while` | 透明、可控、无框架黑盒；符合"不过度依赖大框架" |
| 检索 | 向量 + 结构化加权 | 单靠向量会把"语义相关但产品不同"的 CVE 排进来 |
| 验证引擎 | 独立于 LLM | 验证结果客观、可复现；LLM 不"自己验自己判" |
| 版本比较 | 自实现 | 避免 `packaging` 依赖；启发式，解析失败归 `UNCERTAIN` |
| 持久化 | SQLite | stdlib 可用；`ResultStore` 接口可换 Mongo/MySQL |

**最重要的权衡**：**优先保证正确性、可解释性、可测试性、可扩展性，而不是"看起来像 Agent"**。`MockLLM` + 确定性规划器让整条链路无需 API key 就能端到端跑通并测试，这是本项目的工程立足点。

## 7. 安全边界设计

| 层 | 机制 | 代码位置 |
| --- | --- | --- |
| 目标白名单 | `TargetAllowlist`，deny-by-default，支持 IP/CIDR/hostname/黑名单优先 | `tools/boundary.py` |
| 参数校验 | 每个 `Tool.input_schema` + `validate_against_schema` | `tools/base.py` |
| 禁止任意命令 | LLM 只能请求注册过的 `Tool`，无 shell 能力 | `tools/registry.py` |
| 无破坏性 | `VerificationEngine.non_destructive_only` 拦截破坏性验证器 | `vulnerability/verifier.py` |
| 超时 | 所有 socket/http 操作带 `timeout` | `tools/netutils.py` |
| 执行日志 | `ToolRegistry.call` 记录每次调用 | `tools/registry.py` |
| 密钥 | API key 走环境变量，配置与代码分离 | `config/loader.py` |

**为什么"LLM 不直接执行 shell"这么重要**：一旦给模型 shell 权限，就等于把"命令注入/越权"风险交给一个不可靠的生成器。把能力收窄成"6 个参数严格校验的工具"，攻击面就从"任意命令"缩小到"这 6 个函数 + 白名单内的目标"。

## 8. 如何扩展系统

### 8.1 新增一个工具

1. 继承 `Tool`，填 `name/description/input_schema/output_schema`，实现 `execute`。
2. 在 `pipeline/factory.py` 里 `registry.register(YourTool(...))`。
3. 若 Agent 需要用到它，在 `planner.py` 的决策逻辑里加分支（或让真实 LLM 通过 system prompt 看到它）。

```python
class WhoisTool(Tool):
    name = "whois"
    description = "Query whois info for an authorized host."
    input_schema = {"type": "object", "properties": {"ip": {"type": "string"}}, "required": ["ip"]}
    output_schema = {"type": "object", "properties": {"registrant": {"type": "string"}}}
    requires_network = True

    def execute(self, **kwargs):
        self.scope.assert_allowed(kwargs["ip"])   # 别忘安全边界！
        return {"registrant": "..."}
```

### 8.2 新增一个验证器

1. 继承 `BaseVerifier`，设 `verification_id`，实现 `verify(task) -> VerificationResult`。
2. 在 `VerificationEngine.__init__` 里 `self.register(YourVerifier())`。
3. 在 CVE 数据的 `verification_id` 字段填上对应 key。

### 8.3 接入真实 LLM

```bash
pip install openai
export LLM_API_KEY=sk-...     # Windows: set LLM_API_KEY=sk-...
python main.py ... --provider openai
```

或改 `config/config.yaml` 的 `llm.provider: "openai"`。

### 8.4 换成 Milvus / MySQL / FastAPI

- **Milvus**：实现 `VectorStore` Protocol（`add/search/clear/__len__`），在 `build_system` 里替换 `InMemoryVectorStore`。
- **MySQL/MongoDB**：实现 `ResultStore` 同款接口（`save/load/recent`）。
- **FastAPI**：包一层 `run_workflow` 即可，例如：

```python
@app.post("/analyze")
def analyze(asset: dict):
    system = get_system()               # 应用级单例
    report = run_workflow(Asset.from_dict(asset), system)
    return report.to_dict()
```

## 9. 学习路径建议

按依赖关系由底向上阅读代码：

1. **先读数据模型**（`models/`）：理解 `Asset / Vulnerability / VerificationResult / Report` 与三态枚举 —— 这是全局词汇表。
2. **再读版本比较**（`vulnerability/version.py`）：看 `compare` 和 `version_in_range` 怎么写、怎么测。
3. **然后读 RAG**（`rag/`）：`embedding → knowledge_base → retriever`，理解"向量 + 结构化混合检索"。
4. **再读工具层**（`tools/`）：`base → boundary → registry → 各工具`，理解 schema 校验与白名单。
5. **再读验证引擎**（`vulnerability/verifier.py`）：理解"独立验证 + 无破坏性 + 证据"。
6. **最后读 Agent**（`agent/`）：`state → planner → llm → agent`，理解状态驱动的循环。

配套练习：

- 改 `config.yaml` 的 `rag` 权重，观察 `vulnerability_search` 返回的候选排序变化。
- 给 `data/vulnerabilities/sample_cves.json` 加一条新 CVE，跑一遍看它是否被正确匹配。
- 写一个 `banner_check` 验证器，对着本机起一个假服务试试真实验证。
- 把 `--provider openai` 接上，对比 `MockLLM` 和真实 LLM 的决策轨迹。
